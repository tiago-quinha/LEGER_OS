# 01.12 - Authentication UX, Routing & Security Standards SOP

## Purpose & Scope
This SOP defines the UI layout, authentication hierarchy, server-side routing protections, and privacy compliance standards for **LEGER_OS** on `/login`, `/signup`, `/`, and `/dashboard`.

---

## 1. Authentication Layout Hierarchy

1. **Email/Password Form Priority:**
   - The primary Email & Password inputs sit at the top of the auth card on both `/login` and `/signup`.
   - Submit buttons (*Sign In to Account* / *Register Workspace*) use solid `bg-foreground text-background font-mono text-xs uppercase font-bold tracking-widest` styling with `h-11` heights.

2. **Google 1-Tap OAuth Placement:**
   - Placed below the form, separated by a single clean line divider (`<div className="h-px bg-border/50" />`).
   - Button uses `h-11` with official Google SVG vector icon and natural English copy (*"Continue with Google"* / *"Sign Up with Google"*).

3. **Real Security & Privacy Guarantees Footer:**
   - Underneath the card, display exact, non-jargon user guarantees with dedicated icons:
     ```html
     🔒 256-BIT SSL · 🛡️ ZERO BANK PASSWORDS · 👁️‍🗨️ PRIVATE DATA
     ```
   - Ban buzzword developer jargon (e.g. *"isolated tenant storage"*).

---

## 2. Server-Side Routing Invariants

1. **Root Path Protection (`src/app/page.tsx`):**
   - If `!user`, the server component MUST execute `redirect('/login')` from `next/navigation`.
   - Never return `null` on protected SSR routes, as it renders a blank screen for unauthenticated users.

2. **`/dashboard` Route Alias (`src/app/dashboard/page.tsx`):**
   - Dedicated route handler executing `redirect('/')` to ensure direct access to `/dashboard` resolves cleanly to the primary dashboard view without 404 errors.
